# DECK_RULES.md — KARDS 构筑规则（基于 1950 个公开卡组的统计推断）

> 样本：`_work/decks.json`，**1950** 个公开卡组（2026-11-07 抓自 deck plaza API）。
> 其中剔除 47 个脏数据（快照张数 ≠ 39、单卡副本 > 4、含数据集外卡牌）后，**干净样本 1903 个**。
> 所有数字可由 `node scripts/analyze-decks.mjs` 复现，原始统计见 `_work/deck-stats.json`。
> 实现：`src/data/deckRules.ts` 的 `DECK_RULES` 常量 + `validateDeck()`。

## 1. 方法论

1. **数据获取**：`GET /api/v1/decks?limit=50&page=N`，40 页 → 1950 条（API `meta.total = 3173`，覆盖 61%）。
   每条含 `deck_code`、`cards_snapshot[{card_id,count}]`、`main_faction`、`ally_faction`、`like_count` 等。
2. **脏数据剔除**（47 条）：
   - 快照总张数 ≠ 39（如 17、35、9 张的未完成卡组）；
   - 单卡副本数 > 4（如 39 张同一张卡的恶搞/坏码卡组）；
   - 引用卡牌 API 里不存在的卡（`katzmann`、`1081th_smolensk`，新卡或已移除卡）。
3. **归属判定**：对每张卡同时用 `faction` 与 `host_factions` 判断能否进主/盟军卡组；
   既属主阵营又属盟军的卡计入"主阵营卡"（保守口径，避免高估盟军）。
4. **交叉验证**：deck code 的阵营头（`%%<主><盟>`）与 API 的 `main_faction`/`ally_faction` 交叉核对（1949/1950 一致），
   说明 API 字段本身可靠；卡牌多重集与 code 解码结果的交叉核对见 `docs/DECK_CODEC.md`。

## 2. R1 卡组张数 = 39（极高置信）

全样本张数分布（含脏数据）：

```
39:1934   38:2   35:2   34:1   30:2   26:3   24:1   22:1   17:1   12:1   9:1   0:1     ← 40 张：0 个
```

- 干净样本 **1903/1903 = 100%** 恰好 39 张，均值 = 39，p0 = p50 = p95 = p100 = 39。
- 非 39 张的全部是**未完成/损坏**卡组（9 张、17 张、35 张…），不是"合法但另一种尺寸"。
- 结论：**KARDS 标准卡组固定 39 张**。构筑 UI 应当：39 张时显示"完成"，<39 给 warning，>39 直接 error。

## 3. R2 同名卡上限 = 4（极高置信）

单卡组内"某张卡出现多少张"的分布（干净样本，单位 = 卡组内的一个卡位）：

| 张数 | 出现次数（卡位） | 占比 |
|---|---|---|
| 1 | 21795 | 50.9% |
| 2 | 12513 | 29.2% |
| 3 | 5711 | 13.3% |
| 4 | 2712 | 6.3% |
| **>4** | **0** | **0%** |

最大副本数恒为 4，且 4 张（满编）是常见选择（6.3%），说明"4"是真实上限而不是样本偏差。

## 4. R3/R4 精英卡

- 卡池：275 张 `rarity=Elite`（16.7%）。
- **同名上限 1 张**：14752 个精英卡位里 14751 个是 1 张；唯一 >1 的一例是 3 张（出现在被剔除的脏数据边缘，无法复现于正常卡组）。
- **每卡组精英总张数无上限**：干净样本中每卡组精英张数分布从 0 一直到 39（其中 ≥20 张的有 73 个卡组），
  46 个卡组完全没有精英卡，平均 7.72 张。若存在总量上限（例如 ≤15），不会出现 21 个卡组接近"全精英"。
- 实现上：`eliteCopies: 1`（按卡），`maxEliteTotal: null`（不设总量上限）。

## 5. R5/R6 主阵营 vs 盟军

盟军卡张数分布（干净样本）：

```
0:45  1:2  2:24  3:21  4:41  5:59  6:87  7:99  8:155  9:168  10:220  11:264  12:716  14:1  19:1
```

- **12 张出现 716 次**，是分布的最右密集点（37.6% 的卡组），且 p95 = 12 → **盟军上限 12 张**。
- 主阵营张数分布峰值 **27 = 39 − 12**（716 例），与"盟军 12 张封顶"完全自洽。
- 越界 2 例：14 张（德国+英国）与 19 张（日本+法国），见 §6.1。

## 6. 未定/低置信项与反例

### 6.1 盟军 > 12 的 2 个卡组（0.1%）

| 主 / 盟军 | 盟军张数 | 说明 |
|---|---|---|
| Germany / Britain | 14 | 可能创建于规则变更前，或广场未做构筑校验 |
| Japan / France | 19 | 同上 |

结论：12 张仍是正确规则（99.9% 符合 + 分布峰值），但**校验器对 13~19 张应给 error 还是 warning 可自行决定**；
本项目 `validateDeck()` 给 **error**（与官方构筑器一致），并在 `warnings` 里说明来源是历史卡组。

### 6.2 预备池（reserve）语义未定

- 卡牌 API 有 `pool ∈ {active: 954, reserve: 563, derived: 129}` 与 `is_reserved` 标记。
- 公开卡组里 68.67% 使用了 `is_reserved` 卡牌 → **广场口径下 reserve 卡可自由构筑**。
- 但"reserve"在游戏内可能对应"轮换/预备赛制"（老卡池）。本项目标准赛制暂不拦截，
  `DeckFormat` 已区分 `standard | reserve | draft`，未来要限制只需改 `DECK_RULES.allowReservedInStandard`。
- **置信度：中**（我们只能看到广场允许什么，看不到游戏内赛制开关）。

### 6.3 卡池外的卡

15 张副本引用 `katzmann`、`1081th_smolensk`——卡牌 API 快照里没有这两张卡。
说明卡牌数据与卡组数据**版本不同步**（新卡先出现在卡组里）。导入这类卡组时：
`decodeDeckCode` 会抛"未知卡牌短码"，UI 应提示"卡组含未收录卡牌"并降级只显示已知卡。

### 6.4 未观测到的可能规则

以下规则**无法用广场数据证伪/证实**（广场可能不校验），建议后续用游戏内实测补：

- 卡组**主题/精英数量**相关的成就类限制（不影响构筑合法性）；
- 盟军卡是否还有"按费用/类型"的额外限制；
- 竞技场（draft）与标准赛制的差异（广场没有赛制字段）；
- 卡背/称号等装饰性内容（与本文件无关）。

## 7. 与代码的对应关系

`src/data/deckRules.ts`：

```ts
export const DECK_RULES = {
  deckSize: 39,          // R1
  minDeckSize: 39,
  maxCopies: 4,          // R2
  eliteCopies: 1,        // R3
  maxEliteTotal: null,   // R4（不设总量上限）
  maxAllyCards: 12,      // R5
  maxFactions: 2,        // R7
  allowNeutralCards: true,        // R10
  allowReservedInStandard: true,  // R9（当前口径）
};
```

`validateDeck(deck, cards?)` 返回 `{ valid, errors, warnings, stats }`：

- `errors`：张数超限（>39）、单卡 >4、精英 >1、卡牌不属于主/盟军、盟军 >12、卡牌不在数据集；
- `warnings`：未满 39 张（构筑中）、卡表未加载、盟军 = 主阵营（按无盟军处理）、使用预备池卡；
- `stats`：`{ total, byType, byKredits, units, orders, elite, mainFactionCards, allyFactionCards }`。
